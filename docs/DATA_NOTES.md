# Data Notes: NetsLab 5G Open RAN IDD

## 1. Dataset Overview

The dataset used is the **NetsLab 5G Open Radio Access Network Intrusion Detection Dataset (NetsLab-5GORAN-IDD)**, collected from a live, physical 5G Open RAN testbed at the Network Softwarization and Security Labs (NetsLab), University College Dublin (UCD).

- **Data File**: `data/raw/Network_Dataset.csv`
- **Total Records**: 1,723,817 network flows
- **Total Columns**: 26
- **Missing Values**: 0 across all columns
- **Exact Duplicate Rows (All Columns)**: 83,635 (flows with identical timestamps/attributes logged across repeated probes)

## 4. Label Leakage Analysis & Dropped Columns

To ensure the trained models generalize to real 5G networks rather than memorizing testbed artifacts, the following columns are strictly excluded from feature sets:

1. **`uid`**: Unique transaction hash generated by Zeek. Does not reflect network flow behavior.
2. **`src_ip`**: The testbed uses dedicated attacker machines (e.g. `192.168.0.1` accounts for 484,765 attacks and only 75 benign flows; `172.31.0.134` accounts for 536,058 attacks). Including IP addresses allows models to achieve near-100% artificial accuracy by simply checking the IP prefix.
3. **`dst_ip`**: In the UCD testbed, 1,372,015 attacks (88.4% of all attacks) target the single victim IP `192.168.0.10`. Including `dst_ip` creates a trivial victim-memorization shortcut.
4. **`src_port`**: Ephemeral client ports (64,359 unique values). Randomly assigned by the OS or fixed by specific attack scripts.
5. **`history`**: String representation of Zeek state transitions with 3,796 high-cardinality strings; connection state is already summarized cleanly in `conn_state`.
6. **`attack_category` & `attack_type`**: Ground truth labels preserved strictly for post-scoring metric calculation and per-attack recall analysis.

## 5. Splitting Strategy (Addressing Leakage & Generalisation)

- **Challenge**: The data file `Network_Dataset.csv` is grouped by attack scenario runs. A naive contiguous split would place all benign data in the test split and early attack types in the train split. A purely random shuffle split risks data leakage between sequential flows of the same tool run.
- **Adopted Strategy**:
  - We partition by scenario / `(attack_category, attack_type)` group.
  - Within each group, we perform a sequence-preserving **70% train / 30% test split**.
  - This ensures that:
    1. Every single attack type (all 15 types) is evaluated on unseen test flows.
    2. The unsupervised Isolation Forest (Track A) is trained strictly on the **70% train split of benign flows only** (`traffic_type == 0`).
    3. The supervised XGBoost (Track B) is trained on the **70% train split** using class weighting to balance benign vs attack classes.
    4. The test split contains the held-out **30% of benign and 30% of each attack type**, completely untouched during feature fitting and training.
